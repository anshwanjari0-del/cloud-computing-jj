Practical Cloud Projects

Solidify your theoretical understanding with 5 industry-standard beginner cloud projects. Every project includes specific objectives, prerequisites, numbered steps, expected outcomes, and crucial safety and cost guardrails.

Level: Beginner Estimated Time: 30–45 mins Category: Storage & Web Hosting

1. Host a Static Website Using Cloud Object Storage

Deploy a high-availability, globally reachable HTML/CSS website using AWS S3, Azure Blob Storage, or Google Cloud Storage without maintaining any web servers.

Project Objectives
  • Create an encrypted cloud storage bucket/container.
  • Enable the native static website hosting feature.
  • Configure an explicit bucket policy for public web read permissions.
  • Upload an index.html and test the public HTTP endpoint in a browser.
Prerequisites
  • Free Tier account on AWS, Microsoft Azure, or Google Cloud.
  • A simple text editor (e.g. VS Code or Notepad).
  • Basic knowledge of HTML and web browser developer tools.

Step-by-Step Implementation Guide

1
Prepare Your Local Web Files

Create a local folder containing an index.html and an error.html file with simple heading text such as "Hello from Cloud Storage Website!".

2
Create a Storage Bucket (AWS S3 Example)

Open the AWS Management Console, navigate to S3, and click Create bucket. Choose a globally unique bucket name (e.g., cloudlearn-demo-web-2026) and select your nearest geographic Region (e.g. us-east-1).

3
Enable Static Website Hosting

Under the bucket's Properties tab, scroll down to Static website hosting. Click Edit, select Enable, and designate index.html as your Index document and error.html as your Error document. Save changes.

4
Configure Public Read Access Policy

Under the Permissions tab, disable "Block all public access" for this specific static website bucket. Then add the following read-only Bucket Policy:

JSON Bucket Policy 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadGetObject",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::YOUR-BUCKET-NAME/*"
    }
  ]
}
5
Upload Web Files & Verify Public Endpoint

Upload your index.html and error.html files via the Objects tab. Copy the bucket website endpoint URL (e.g. http://your-bucket.s3-website-us-east-1.amazonaws.com) into an incognito browser window.

Expected Outcome

Your static website loads instantly in any browser anywhere in the world. It requires 0 CPU patches, automatically handles high request volumes, and incurs no ongoing server charges when idle.

Safety & Cost Considerations
1. Security: Never apply public read policies to buckets storing private databases, configuration secrets, or client documents. Only public web assets should have anonymous s3:GetObject rights.
2. Cost: AWS Free Tier provides 5 GB of standard S3 storage and 20,000 GET requests per month for 12 months. Ensure you don't host multi-gigabyte media files without billing alarms.

2. Deploy a Dynamic Web App Using Cloud PaaS

Deploy a dynamic web application (Node.js or Python) using modern Platform-as-a-Service (e.g., Azure App Service, AWS App Runner, or Google Cloud Run) with automated TLS certificates.

Project Objectives
  • Understand Platform as a Service (PaaS) abstraction.
  • Package and deploy code directly without configuring operating systems.
  • Observe automatic HTTPS provisioning and environment variables.
  • Inspect application streaming logs via cloud console.
Prerequisites
  • A free GitHub account.
  • Cloud account with Azure (Free App Service Plan F1) or Google Cloud (Free Tier Cloud Run).
  • A basic 5-line Node.js or Python Flask web script.

Step-by-Step Implementation Guide

1
Create a Minimal Web Application Repository

Create a public or private GitHub repository named cloud-sample-app. Include a simple server.js file that listens on process.env.PORT || 3000 and returns an HTTP response: "Application deployed successfully on Cloud PaaS!".

2
Provision the PaaS Web App Service

In Azure Portal or Google Cloud Console, select Create a Resource → Web App (Azure App Service) or Cloud Run. Select your language runtime (e.g., Node 18 LTS) and select the Free F1 Tier (on Azure) or Serverless per-request pricing.

3
Connect Deployment Center via GitHub

Under the Deployment Center blade, authorize GitHub and select your repository and branch. The cloud provider automatically commits a GitHub Actions CI/CD workflow YAML file to your repository.

4
Verify Live Application & Check Diagnostic Logs

Wait for the build workflow to finish (typically 90 seconds). Access your allocated domain (e.g. https://your-app.azurewebsites.net). Notice that a valid SSL/TLS certificate is already installed automatically! Open Log Stream in the portal to watch live HTTP request logs.

Expected Outcome

A production-grade, secure HTTPS dynamic web application running with automatic scaling and automated Git push-to-deploy workflows without managing any underlying Linux or Windows server.

Cost & Teardown Tip
Select the Free (F1) App Service plan on Azure or Google Cloud Run's generous 2 million free monthly requests tier. Once finished testing, you can stop or delete the resource group to prevent accidental plan upgrades.

3. Design a Fault-Tolerant Multi-Tier Cloud Architecture Diagram

Design an industry-standard, resilient 3-tier web architecture diagram incorporating VPC segmentation, load balancing, multi-AZ auto-scaling, and managed database replicas.

Project Objectives
  • Learn the standard 3-tier architecture pattern (Presentation, Application, Data).
  • Design strict subnet boundaries (Public vs Private) using CIDR notation.
  • Incorporate redundant Availability Zones for Zero-Downtime resilience.
  • Use free diagramming tools (draw.io or Lucidchart) with official cloud icon packs.
Prerequisites
  • A free web browser and an account on diagrams.net (draw.io).
  • Understanding of VPC, subnets, and load balancers from Learn Module 08.

Step-by-Step Implementation Guide

1
Establish Outer Boundaries (Cloud, Region, & VPC)

Open draw.io. Draw a large container representing your Cloud Region (e.g. AWS us-east-1). Inside, draw a dashed rectangle representing the VPC with CIDR block 10.0.0.0/16. Connect an Internet Gateway to the perimeter.

2
Design Public Subnets & Application Load Balancer (Tier 1)

Draw two columns representing Availability Zone A (AZ-1a) and Availability Zone B (AZ-1b). In each, draw a Public Subnet (10.0.1.0/24 and 10.0.2.0/24). Place an Application Load Balancer (ALB) spanning both public subnets to distribute inbound internet requests.

3
Design Private Compute Subnets with Auto-Scaling (Tier 2)

Below the public tier, draw two Private App Subnets (10.0.10.0/24 and 10.0.11.0/24). Place an Auto Scaling Group with EC2 instances or container pods inside. Configure outbound internet updates through a NAT Gateway in the public subnet.

4
Design Private Database Subnets with Multi-AZ Replication (Tier 3)

Draw isolated Private Data Subnets (10.0.20.0/24 and 10.0.21.0/24). Place a Primary Database in AZ-1a with automated synchronous replication to a Standby DB in AZ-1b for automatic failover. Add arrows demonstrating traffic flow strictly from Tier 2 to Tier 3.

Expected Outcome

A portfolio-ready, professional systems architecture diagram demonstrating how enterprise cloud solutions eliminate single points of failure (SPOF) and protect database layers behind defense-in-depth security zones.

Architectural Best Practice
Always enforce security groups as virtual firewalls: Tier 1 (ALB) accepts HTTP 80 / HTTPS 443 from 0.0.0.0/0; Tier 2 (Compute) accepts port 80/8080 only from Tier 1's Security Group; Tier 3 (Database) accepts port 3306/5432 only from Tier 2's Security Group.

4. Provision a Linux Virtual Machine & Configure an Nginx Web Server

Launch an Ubuntu Linux cloud virtual machine (AWS EC2, Azure VM, or Google Compute Engine), configure Security Group firewall rules, SSH into the machine, and install an Nginx web server.

Project Objectives
  • Launch a Free-Tier eligible VM instance (e.g. t2.micro or B1s or e2-micro).
  • Generate and safely protect an SSH keypair (.pem file).
  • Configure inbound firewall rules (Port 22 SSH & Port 80 HTTP).
  • Connect via SSH terminal and install the Nginx web server.
Prerequisites
  • Cloud account on AWS, Azure, or GCP.
  • A terminal application (Terminal on macOS/Linux, PowerShell or Git Bash on Windows).
  • Basic knowledge of command-line terminal commands.

Step-by-Step Implementation Guide

1
Launch the Free-Tier Virtual Machine

Navigate to EC2 → Launch Instances (AWS) or Virtual Machines → Create (Azure). Select Ubuntu 22.04 LTS and the Free-Tier eligible instance size (t2.micro on AWS or Standard_B1s on Azure).

2
Generate and Secure an SSH Key Pair

Select Create new key pair named cloudlearn-key.pem. Download the private key file. On Unix or macOS terminals, restrict permissions to read-only for your user:

Bash / Terminal 
chmod 400 cloudlearn-key.pem
3
Configure Security Group Rules

Add two inbound firewall rules:
• Type: SSH (Port 22): Source: My IP (Best practice: restrict SSH access to your current IP).
• Type: HTTP (Port 80): Source: 0.0.0.0/0 (Anywhere) (To allow public web browsing).

4
Connect via SSH and Install Nginx

Once the VM reaches Running status, copy its Public IPv4 Address. Open your terminal and connect:

Bash / SSH Connection 
# Connect to instance
ssh -i "cloudlearn-key.pem" ubuntu@YOUR_PUBLIC_IP

# Update packages and install Nginx web server
sudo apt update && sudo apt install -y nginx

# Verify Nginx service is running
sudo systemctl status nginx

Open your web browser and navigate to http://YOUR_PUBLIC_IP. You will see the default "Welcome to nginx!" landing page rendered directly by your cloud virtual machine.

Expected Outcome

A functional Linux server running in an isolated cloud data center, protected by security groups and serving web traffic over port 80.

CRITICAL COST RULE: Terminate When Finished!
Even under Free Tier limits (750 hours/month on AWS), running multiple virtual machines or leaving high-performance disks allocated will incur charges. Once you have verified the Nginx web page, go to the console, click Instance State → Terminate (or Delete on Azure).

5. Design an Automated Cloud Backup & Disaster Recovery Plan

Establish quantifiable RPO and RTO goals, configure automated daily snapshot lifecycle policies for cloud storage and databases, and design cross-region disaster recovery replication.

Project Objectives
  • Define concrete Recovery Point Objective (RPO) and Recovery Time Objective (RTO).
  • Configure an automated backup lifecycle policy using AWS Backup or Azure Backup.
  • Enable Cross-Region Replication (CRR) for critical object storage buckets.
  • Document an actionable, step-by-step restore test procedure.
Prerequisites
  • Cloud account with AWS or Azure console access.
  • Understanding of cloud storage tiers (Module 07) and High Availability (Module 10).

Step-by-Step Implementation Guide

1
Define RPO & RTO Service Level Agreements (SLAs)

Establish business targets:
• RPO = 1 hour: Maximum acceptable data loss duration. Means backups/snapshots must occur at least hourly for production databases.
• RTO = 30 minutes: Maximum acceptable recovery time before services are back online. Requires pre-scripted automation templates (Infrastructure as Code).

2
Configure an Automated Backup Plan (e.g., AWS Backup)

Open AWS Backup (or Azure Backup Center). Create a new Backup Plan named Daily-Production-Policy. Define a schedule: Run daily at 02:00 UTC, transition cold data to Glacier / Archive storage after 30 days, and automatically expire backups after 90 days.

3
Enable Cross-Region Storage Replication

Select your primary S3 bucket in us-east-1 (N. Virginia). Open the Management tab and click Create replication rule. Set the destination to a paired disaster recovery bucket in us-west-2 (Oregon). This protects business assets against a catastrophic regional power grid or telecommunication outage.

4
Conduct a Simulated Recovery Drill

The true test of a backup plan is the restore process. Simulate accidental data deletion: Delete a non-critical test database table. Navigate to your backup vault, select the latest recovery point, and restore to an alternate test instance. Validate that data integrity matches the pre-deletion state and record the total elapsed restoration time.

Expected Outcome

A fully automated, compliant disaster recovery framework ensuring business continuity with verified recovery points and automated cross-region data resilience.

Storage Lifecycle Cost Optimization
Keeping hundreds of full disk snapshots in active storage is expensive. Always configure Lifecycle Transitions that automatically migrate historical backup snapshots to deep archive tiers (such as AWS S3 Glacier Deep Archive at $0.00099 per GB/month).
